# 路线一样，为什么效果比不上 StableGen（2026-11-05 逐项定位）

> 对照源码：`D:\code\gen\others\StableGen-main`（v0.4.x，约 3 万行）
> 本文只列**代码证据**，不猜。每条都带文件名 + 行号。
> 本轮已落地的改动与实测数字见文末第七节。

## 结论先行

**「多视图扩散 → 投影 → bake」这条路线名相同，但 Qwen 输出在管线里的角色
完全不同：StableGen 把它当「补丁」，meow3d 把它当「整张替换」。**

再叠加三个放大器：起点不同（白模 vs 已带贴图）、采样配置不同（20 步无蒸馏
vs 8 步 Lightning）、相机/权重/闭环的工程完整度差一个数量级。
所以差距不是「调参没调好」，是**语义层级就走岔了**。

---

## 一、最致命：补丁 vs 整幅替换

StableGen 的 `sequential` 不是「每个机位独立出一张新贴图」：

```python
# stablegen/texturing/generator.py:1874-1880
elif context.scene.generation_method == 'sequential' and self._current_image > 0:
    render_info = ... "inpaint", subtype="render"     # 当前已投影纹理的渲染
    mask_info   = ... "inpaint", subtype="visibility" # 可见性/未覆盖 mask

# :1955-1975  每个后续机位先渲 context + visibility，再生成
yield from export_visibility(context, ..., camera_render=_cur_cam, ...)
yield from export_emit_image(context, ..., fallback_color=fallback_color, ...)
```

提示词把这件事写死在模型约束里：

```python
# stablegen/texturing/workflows.py:928-945  QWEN_21_DEFAULT
"Edit image 2 into '{main_prompt}'. Preserve its existing "
"non-magenta textured regions. Replace every solid magenta "
"region with texture that seamlessly continues the surrounding "
"surface. Use image 1 only as a geometry and composition guide."
```

而且有四道护栏**从工程上保证已贴好的像素不被改写**：
`_apply_qwen_binary_context_mask` (`generator.py:520`)、
`_dilate_qwen_context_fallback` (`:667`)、
`_apply_qwen_context_cleanup` (`:711`)、
`_reject_qwen_fallback_writes` (`:626`)。

meow3d 旧路径（`tools/run_guided.py` 改写前）是四个机位**各自整幅重绘**，
再用 `bake_projection.py` 把整张图铺进 UV 图集。已正确的原生贴图被全盘覆盖，
8 步 Lightning 的画风漂移 100% 继承 —— 用户自己的实测（`out/asuka_style_test.png`）
已经写明：橙发变浅金、正红战服变亮、赛璐璐变半写实、边缘发软。

## 二、起点不同：白模 vs 已带贴图

| | StableGen | meow3d（旧） |
|---|---|---|
| 输入网格 | TRELLIS.2 白模，**没有贴图** | `asuka_Textured_00001_.glb`，**自带完整贴图** |
| Qwen 的角色 | 唯一颜色来源 | 把已经对的贴图再「发明」一遍 |
| 因此 | 重绘是必需 | 重绘是**净损失** |

`docs/与StableGen的差距-实测定位.md` 第二节已量出这一步是负收益，但没把
「起点不同」这层说透。同一套代码搬到一个已经贴好图的网格上，语义就反了。

## 三、生成模型与采样参数（几乎每一项都不同）

| 项 | StableGen `QWEN 2.1 PRECISE` | meow3d 旧默认 |
|---|---|---|
| 模型调用 | `TextEncodeQwenImageEditPlus`，`image1/2/3` 三个语义槽 | `Engine.txt2img_pipe()` 传一张 `image` |
| 输入图 | **3 张**：几何引导 / 已投影上下文（品红 mask）/ 整体外观参考 | **1 张**（beauty），`--reference` 实际未使用 |
| steps | **20** | **8** |
| cfg | 1.0 | 1.0 |
| sampler | `dpmpp_sde` + `sgm_uniform` | 默认 Euler / simple |
| Lightning LoRA | **无** | `qwen21_lightning`，并强制 `steps=min(steps,8)` |
| 输出 | **native RGBA**，透明像素排除投影 | 浅灰底 + BiRefNet 事后抠图 |
| 权重指数 | 7.0（预设）/ 成品 15.0 | 3.0（CLI 默认），run_guided 8.0 |

证据：
- `stablegen/ui/presets.py:88-110` —— 20 步 / CFG1 / DPM++ SDE / SGM Uniform / `lora_units: []` / `qwen_image_21_native_rgba: True`；描述里直写「produced broad, coherent panels that followed the model silhouette」。
- `stablegen/util/workflow_templates.py:1285-1300` —— Qwen Edit 模板。
- `stablegen/texturing/workflows.py:189, 611-631` —— `image1/image2/image3` 槽位装配。
- `meow3d/tools/qwen_guided_views.py:166-175` —— 挂 Lightning 且把步数夹到 8。
- `meow3d/tools/qwen_guided_views.py:216-227` —— **`--ref` 空转**：单图模式下
  `imgs = []` 后只 append beauty，`ref_sq` 仅在 `if not imgs` 兜底分支用到。
  也就是说 run_guided 一直传 `--reference`，但它**根本没进模型**。

> 主项目 `2d-game-meow/workflows/engine.py:740-750` 自己的实测也写着：
> 「8~12 步浅色主体对比度不够、细节发白，16 步起才稳定」。
> 8 步蒸馏用于 32~128px 精灵图是够的，用于 3D 贴图是明显欠采样。

## 四、相机布置

| | StableGen | meow3d |
|---|---|---|
| 数量 | 默认 **8**（2–32） | 固定 **4** |
| 放置 | `normal_weighted`（面法线面积加权 K-means）/ `greedy_coverage`（覆盖率目标 0.95，BVH 验证可见性） | 方位角等分 `i*360/N` |
| 俯仰 | 有 elevation，且可 clamp 避免极端顶/底视 | `elevation = 0.0` 全水平 |
| 画幅 | Auto Aspect Ratio / Fit camera resolution，按轮廓自适应 | 固定 `ORTHO=2.8`，角色仅占约 73% 画幅 |

证据：`stablegen/core/properties.py:1048-1062, 1106-1142`；
`stablegen/cameras/placement.py:59-85, 524-635`；
`meow3d/meow3d/projection/guidance.py:camera_list`、`bake.py:ORTHO=2.8`。

4 个水平环绕相机覆盖不到头顶、肩窝、腋下、脚底；局部细节被 1024² 视图
压到 ~90px 头部，再投进 2048² 图集要放大 6~8 倍 —— 这是「糊」的直接来源。

## 五、投影混合与遮挡

StableGen 在 **3D 表面逐点**算，不是 UV texel 反向采样：

```osl
// stablegen/raycast.osl:56-75
if (trace(Origin, d)) {                       // 真光线遮挡
    getmessage("trace", "hitdist", Distance);
    if ((Distance + RayEpsilon) < threshold) Result = 0;
    else {
        float orthogonality = max(-dot(d, normalize(SurfaceNormal)), 0);
        if (angle > AngleThreshold) Result = 0;
        else Result = pow(orthogonality, Power);
    }
}
```
配 `feather.osl:58-62` 视锥边缘平滑、DPPG 3px 边界带 + 12px 羽化
（`sg_silhouette_margin`、`sg_silhouette_feather`）、AQW 采集质量加权
（`texturing/confidence.py`）、CGC 置信度门控、逐像素 max 归一化、
`util/color_match.py` 多视图接缝配色，且**生成期 discard 50° / 成品 90° 分两阶段**
（`presets.py:169-181`）。

meow3d：Z-pass 深度图近似遮挡 + `max(dot(N,-cam_dir),0)^k` + alpha
（`tools/blender_bake_views.py:158-215`）。没有 raycast、DPPG、边缘羽化、
AQW、CGC、颜色匹配，也没有分阶段 discard。

混合参数重算，不能增量修某一块。

### ⚠️ 8 机位第一次跑暴露的静默失败（已修）

```
Warning: Cannot add more than 8 UV maps
AttributeError: 'NoneType' object has no attribute 'data'   # proj.data.foreach_set
Blender quit
 合并完成：覆盖 84.6% … 视图 7 个        ← 宿主侧仍「成功」导出
```

`blender_bake_views.py` 原来给每个视图 `mesh.uv_layers.new(name="ProjUV_"+key)`，
而 Blender 单个 mesh 的 UV layer 上限是 **8**：第 8 个返回 `None`，
`foreach_set` 抛异常；但 `blender -b -P` 里的 Python 异常**仍以 0 退出**，
宿主 `subprocess.run(check=True)` 抓不到，于是静默少烘一个视图。

修了两层：

1. **根因**：循环外只建一个 `ProjUV`，每轮 `foreach_set` 覆盖坐标，机位数
   不再受 UV layer 上限约束。
2. **护栏**：`bake.verify_baked_views()` 在合并前强制核对
   `*_color.npy` 数量与期望视图名；非 reproject 时先删旧 npy（否则残留会
   混进 `merge()` 并掩盖缺失）。新增 3 条回归单测
   （`tests/test_bake_guard.py`）。

## 十、第三轮：裁满画幅（以及一个反直觉的结论）

### 做了什么

原来 `ORTHO=2.8` 写死，模型归一化后最大跨度只有 2.0 → 角色在 1024² 视图里
只占 71.5%，头部约 90px，投进 2048² 图集要放大 6~8 倍。这一轮把它变成
**全链路统一的可配置画幅**：

* `bake.fit_ortho(V, angles, margin)` —— 按所有相机方向下模型的最大投影跨度
  算最小安全 ortho，默认 `margin=1.08`（留 8% 边距；取 1.0 会被扩散模型
  裁掉贴边的头发/脚尖）；
* `projection_bbox` / `bake.run` / `guidance.render` 都加 `ortho` 参数，
  由 `--ortho` 或 `--fill-frame` 同步传给 guidance / refine / bake，
  **五个环节共用同一套画幅**（和上一轮统一相机角度同理）；
* 画幅变了会**强制重渲指引图**、禁用 `--reuse-views`、禁止 Reproject 复用
  旧 npy（`bake_config.json` 里记了 ortho，不一致直接报错）。

```bash
.venv/Scripts/python.exe tools/run_guided.py <网格.glb> \
    --reference <原图.png> --out out/xxx.glb --fill-frame
# 或显式给值（所有子命令都吃 --ortho）
```

### 实测（Asuka，4 机位 / 20 步 / flat 精修，完整链路 2m55s）

| 指标 | 2.8 默认 | **2.16 裁满** |
|---|---|---|
| 正交视野边长 | 2.8 | **2.16** |
| 角色在 flat 图里的高度 | 732 px | **948 px（+29.5%）** |
| 占画幅 | 71.5% | **92.6%** |
| 头发/脚尖 | 完整 | **完整，未被裁** |
| bake 覆盖率 | 80.9% | 80.8% |
| 贴图相对原生 \|ΔRGB\| | 0.0759 | 0.0747（-1.6%） |
| 同指标 p90 | 0.1882 | 0.1843 |
| 覆盖区高频能量 | 0.0301 | 0.0310（+3.0%） |

视图对比 `out/fillframe_views_compare.png`，3D 预览
`out/asuka_fillframe_views.png`。

### ⚠️ 反直觉：分辨率 +29.5%，最终贴图只改善 3%

怀疑是 `--protect 0.85` 把收益挡掉了，于是把保护强度降到 0.5 做了对照：

| 配置 | \|ΔRGB\| | 高频能量 |
|---|---|---|
| protect 0.85 / 2.8 | 0.0759 | 0.0301 |
| protect 0.85 / 2.16 | 0.0747 | 0.0310 |
| protect 0.50 / 2.8 | 0.0975 | 0.0313 |
| **protect 0.50 / 2.16** | 0.0971 | **0.0323** |

放行更多像素后，画幅带来的高频增益仍只有 **+3.2%**，色差几乎不变。
**结论：当前「糊」的根因不是 Qwen 视图分辨率，而是 UV 图集的 texel 密度。**
带贴图路线的底图本来就是 2048² 原生贴图直出，不缺分辨率；投影只补约 22%
像素，且主要是低频修复，所以源视图从 732px 提到 948px 传不到最终贴图上。

这也解释了为什么第九节里「20 步 vs 8 步」同样只有 -4.1% ——
**保护性合成会系统性地稀释所有上游生成质量的改进**。这是这套架构的固有性质，
不是 bug。

### 那这轮的价值在哪

1. **给白模路线铺路**：从 `MeshOnly` 白模出发、`--protect 0` 时，Qwen 是唯一
   颜色来源，视图分辨率**直接等于**贴图分辨率，那 +29.5% 会全额兑现。
   这是下一步最该做的 A/B。
2. **统一了画幅参数**：以前 ortho 散落在 4 个文件、任何一处改了都会静默错位；
   现在单一来源 + 缓存校验，8 机位 / 带俯仰角时不会再出现「图对不上」。
3. **纠正了归因**：省下继续在「让 Qwen 出更大图」上投入的时间，
   真正的下一站是 **UV 重展开 / 提高图集 texel 密度**（当前 keep 原生 xatlas
   碎片 UV 只覆盖约 55.9% texel），或 DPPG / 边缘羽化治接缝。

新增 `tests/test_fill_frame.py` 6 条单测（含「收紧后 8 个视角都不裁切」
与「画幅变了禁止 Reproject」），全量单测 **56 passed**。

## 十一、第四轮：白模路线验证（真正不依赖 NVIDIA 原生贴图的链路）

### 为什么必须单独验证

`asuka_WhiteMesh_00001_.glb` **既没有 UV 也没有 baseColorTexture**（trimesh 实测：
`uv=None`、`mat=None`）。所以：

* `unwrap=keep` 会直接报错，`glbpatch.patch_base_color` 也找不到贴图；
  必须 `--unwrap smart` 走 Blender 重新展开 + 重导出（51.6MB GLB）。
* **白模渲出来的 flat 是纯白**（前景均值 `[0.983,0.984,0.986]`，通道间差
  只有 0.003）。拿它做 YUV 颜色锚定会把 Qwen 刚生成的橙发/红战服全部拉成白，
  保护性合成也会把白底混进贴图 —— 是灾难而非改善。

### 两个代码修正

1. `refine.has_color_reference(rgb, mask, min_spread=0.06)`：用前景的
   通道极差判断底图是否携带可信颜色（带贴图 flat 约 0.2~0.6，白模 0.003）。
   判定不可信时 `refine_views.py` **跳过颜色锚定与保护性合成**，只保留同机位
   对齐，让 Qwen 输出成为唯一颜色来源。
2. `--white-mesh` 一键开关：自动设 `protect=0` / `unwrap=smart` /
   `--two-images`（把参考图注入 Qwen，白模自己没有颜色可抄）。

```bash
.venv/Scripts/python.exe tools/run_guided.py out/meow3d/asuka_WhiteMesh_00001_.glb \
    --reference out/in/asuka.png --out out/xxx.glb --white-mesh --fill-frame
```

### 双图 Qwen 在白模上不拼图

之前带贴图路线上两张全身图会画成「左原图 / 右结果」两格（汉服两次中招）。
这轮白模 + `--two-images` + 20 步实跑 4 视图，**全部是单角色、无拼图**，
橙发 / 红战服 / 蓝眼 / T-pose 全部正确，金属扣、缝线、胸前编号 02 等细节
甚至比原生贴图更丰富。原因推测是白模 beauty 是灰白素模，与参考图差异极大，
模型更容易区分「结构参考」与「外观参考」两个角色。

### 严格画幅 A/B（控制变量，同一批 Qwen 出图）

没有重跑两套 Qwen，而是把同一批 2.16 视图**整体缩放 0.7714 = 2.16/2.8**
并居中，模拟等效 2.8 构图 —— 内容完全相同，只差有效分辨率：

| 指标 | 2.8 等效 | **2.16 裁满** |
|---|---|---|
| refine 前景占比 | 8.3% | 13.9%（正好 0.771² 的倒数） |
| bake 覆盖率 | 26.4% | 26.6% |
| atlas 覆盖区高频能量 | 0.0404 | **0.0434（+7.4%）** |
| 两版覆盖区平均色差 | — | 0.0879 |

**白模路线的画幅收益（+7.4%）确实是带贴图路线（+3.0%）的 2.5 倍**，
印证了第十节的判断：保护性合成会稀释上游改进，白模没有可信底图可锁，
所以分辨率更直接地传到贴图。但 +29.5% 仍没有全额兑现 —— 因为还有更硬的
瓶颈。

### 新瓶颈：UV texel 利用率，不是画幅

| | 单视图权重覆盖 | 多视图并集 |
|---|---|---|
| 白模 smart UV / 4 水平机位 | 8.8~12.1% | **26.6%** |
| 带贴图 keep UV / 8 normal-weighted 机位 | 28.7~32.8% | **85.7%** |

白模 4 个视图几乎不重叠（12.1+8.8+10.2+8.9 ≈ 26.6），说明不是相机角度不够
互补，而是 **smart unwrap 后 UV 岛本身只占约三成 texel**，73% 的图集靠
扩散填充，侧视因此出现杂色条纹。这正好把前几轮的结论闭环了：
**「糊」的根因始终是 UV 图集 texel 密度**。

### 下一步（优先级已重排）

1. **白模 8 机位 + normal-weighted**：并集有望从 26.6% 提到 50%+；
2. **换 UV 展开**：StableGen 官方给 TRELLIS.2 稠密网格推荐 `Cube Project`，
   或提高 atlas 到 2048²；
3. **UV 空间补洞 / 颜色匹配**：把 73% 扩散区改成基于邻域视图的合理外推；
4. 之后才轮到 DPPG / 边缘羽化 / AQW。

新增 `test_has_color_reference_distinguishes_white_mesh`，全量单测
**57 passed**；`--white-mesh --fill-frame --reuse-views` 端到端复跑通过
（4/4 视图、覆盖 26.8%）。

## 十二、第五轮：覆盖率是个会骗人的指标（以及真实瓶颈定位）

### 一开始以为找到了杠杆

沿第四轮「UV texel 利用率」的结论，扫了一遍 UV / 分辨率 / 边缘扩张组合，
全部复用同一批白模 Qwen 视图（不重跑生成）：

| 配置 | 全图覆盖率 | 结论 |
|---|---|---|
| smart / 1024 / margin 4（基线） | 26.6% | — |
| smart / **2048** | **19.8%** | 加大图集反而更差 |
| cube / 1024 | 25.6% | 数字相近但视觉串色 |
| cube / 2048 | — | **Blender EXCEPTION_ACCESS_VIOLATION (exit 11)** |
| smart / margin 16 | 57.2% | — |
| smart / margin 32 | 78.8% | — |
| smart / margin **64** | **89.4%** | 「超过」带贴图 8 机位的 85.7% |
| smart / 降面 10 万 / margin 16 | 80.0% | GLB 从 51.6 → 10.1 MB |
| smart / 降面 5 万 / margin 16 | 81.4% | GLB 4.9 MB |
| smart / 降面 2.5 万 | — | **exit 11** |

### ⚠️ 但 margin 64 的四视角预览和基线几乎逐像素相同

`--margin` 是 Blender bake 的边缘扩张，对 **碎片 UV**（smart unwrap 把 49 万面
拆成成千上万个微小岛）会把颜色涂到 **UV 岛外的空白 texel**。那些 texel
渲染时没有任何三角形采样 —— 覆盖率涨了 63pp，画质一点没变。

手动解析 GLB 的 `TEXCOORD_0` + indices 光栅化 UV 岛后，真相是：

| 配置 | 全图覆盖 | **UV 岛占用** | **岛内覆盖** | 岛外虚高 |
|---|---|---|---|---|
| smart m4 | 26.6% | 14.7% | **79.0%** | 17.6% |
| smart m32 | 78.8% | 14.7% | **87.8%** | 77.2% |
| smart m64 | 89.4% | 14.7% | **89.8%** | 89.3% |
| cube m4 | 25.6% | 26.1% | 86.8% | 4.0% |
| smart 2048 | 19.8% | 12.4% | 87.0% | 10.4% |
| **降面 5 万 / smart / m4** | 55.1% | **28.1%** | **89.3%** | 41.7% |

真正有贡献的只有岛内那 **79% → 89.8%（+10.8pp）**；
smart unwrap 的 UV 岛**只占 14.7% 图集**，剩下 85% 全是浪费。

### 代码固化

新增 `meow3d/projection/uvstats.py`：直接解析 GLB 的 `TEXCOORD_0` 与
primitive **顶层** `indices`（trimesh 对 Blender 中间 GLB 会给出
`visual.uv=None`，而在 glTF 里 indices 本来就不在 `attributes` 里 ——
第一版正是踩了这个坑静默返回 None），光栅化出 UV 岛 mask，
`coverage_stats()` 给出四个数：`coverage`（旧口径）/ `uv_usage` /
`coverage_uv`（真正影响渲染）/ `coverage_ghost`（纯浪费）。

`bake.run()` 已在合并后自动统计并打印；`margin >= 16` 且虚高超过岛内覆盖
时会明确警告；`bake_projection.py` 对两组实测崩溃参数给出提前提醒。
新增 `tests/test_uvstats.py` 5 条单测（含「只涂岛外」的回归用例）。

### 其它两条否定结论

* **Cube Project 不能当默认**：UV 占用翻倍到 26.1%、虚高只有 4%，
  但多个面投到同一区域互相覆盖 → 头发/脸上出现红色串色斑点，视觉明显更差。
  StableGen 官方推荐它给稠密网格，前提是人家的投影材质在 **3D 表面点**算权重，
  我们是在 UV texel 上 bake，重叠就直接串色。
* **加大图集分辨率没用**：2048² 让 UV 占用从 14.7% 降到 12.4%。

### 最佳配置与白模一键开关

`--white-mesh` 现在自动加 `--decimate 50000`（`--decimate 0` 可关）：

```
UV 岛占用 14.7% → 28.2%，岛内有效覆盖 79.0% → 89.2%，
GLB 51.6MB → 4.9MB，端到端 --white-mesh --fill-frame --reuse-views 通过
```

侧视残留的杂色条纹**不是 UV 造成的** —— 它来自 Qwen 侧视图本身的内容
（侧视角色手臂/胸口被画成杂色）。所以下一步应该是 **8 机位 / 改善侧视生成
质量 / Local Edit 局部修**，而不是继续调 UV 或 margin。

全量单测 **62 passed**。
